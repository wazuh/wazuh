# Inventory Sync Server Schemas

The wire contract between agents and the manager is a single FlatBuffers schema:

- **Schema file:** `src/shared_modules/utils/flatbuffers/schemas/inventorySync.fbs`
- **C++ namespace:** `Wazuh.SyncSchema`
- **Root type:** `Message` (a union envelope whose payload for synchronization is `FullSession`)
- **Generated header:** `src/shared_modules/utils/flatbuffers/include/inventorySync_generated.h`,
  produced by the `compile_schemas_input` CMake target (the header is generated at build time;
  the `.fbs` file is the single source of truth). It can be regenerated by hand with
  `external/flatbuffers/build/flatc -c -o src/shared_modules/utils/flatbuffers/include <schema>`.

The manager-side consumer is this module alone: remoted relays the body opaquely (the authenticated
identity travels in the `X-Wazuh-Agent-Id` header), and the anti-spoofing gate is this module's own
cross-check of `Start.agentid` against that header (`403` on mismatch). The module's code never names
the namespace directly — it goes through the `invsync::schema::fb` alias (`src/schema/syncSchema.hpp`),
the one place that binds to the generated code.

## The envelope

```text
Message { content: MessageType }          // root_type

union MessageType {
    DataValue,        // = 1
    DataClean,        // = 2
    ChecksumModule,   // = 3
    Start,            // = 4
    DataContext,      // = 5
    FullSession       // = 6
}
```

A synchronization request is always `Message{FullSession}`. The other union members exist so the
individual tables remain addressable message types; the server rejects anything that is not a
`FullSession` with `400`.

## FullSession

```text
table FullSession {
    start: Start;
    payload: SessionPayload;
}

union SessionPayload {
    SyncData,         // = 1
    Cleans,           // = 2
    ChecksumModule    // = 3
}
```

A whole synchronization session is ONE message: `Start` (who/what/how) plus exactly one payload.
Re-applying the same session is idempotent, so a retry is simply a re-POST of the same buffer —
there are no acknowledgment messages, no sequence numbers, and no retransmission protocol in the
schema, by design.

## Start

```text
table Start {
    module: string;            // e.g. "syscollector", "fim", "sca"
    mode: Mode;
    index: [string];           // the indices this session targets
    option: Option;
    architecture: string;      // agent/OS metadata, stamped onto documents
    hostname: string;
    osname: string;
    osplatform: string;
    ostype: string;
    osversion: string;
    agentversion: string;
    agentname: string;
    agentid: string;           // MUST match remoted's authenticated id (403 otherwise)
    groups: [string];
    global_version: ulong;     // guards metadata/group updates against stale writers
    cluster_name: string;      // MUST match the manager's cluster (403 otherwise)
    feed_offset: ulong;        // agent-reported feed position; carried in the schema, not read by this module's pipeline
}
```

## Payload tables

```text
table SyncData {                     // ModuleDelta data
    values: [DataValue];             // >= 1 required
    contexts: [DataContext];         // optional; vulnerability-detection context data
}

table DataValue {
    operation: Operation;            // Upsert | Delete
    id: string;                      // document id within the agent's scope
    index: string;                   // target index (allowlisted per document)
    version: ulong;                  // > 0 -> versioned upsert
    data: [byte];                    // the document, as JSON bytes
}

table DataContext {                  // like DataValue, minus operation/version
    id: string;
    index: string;
    data: [byte];
}

table Cleans {
    items: [DataClean];              // >= 1 required
}

table DataClean {
    index: string;                   // one index to wipe for this agent
}

table ChecksumModule {
    index: string;                   // the index to verify
    checksum: string;                // the agent's aggregate checksum
}
```

## Enums (pinned discriminants)

The numeric values are part of the wire contract — reordering an enum silently changes what every
deployed agent sends. `schemaRoundtrip_test.cpp` in the module's unit suite pins each of these, so
a drift fails a test instead of becoming a fleet-wide protocol bug.

| `Mode` | value |
|---|---|
| `ModuleDelta` | 0 |
| `ModuleCheck` | 1 |
| `MetadataDelta` | 2 |
| `MetadataCheck` | 3 |
| `GroupDelta` | 4 |
| `GroupCheck` | 5 |

| `Option` | value |
|---|---|
| `Sync` | 0 |
| `VDFirst` | 1 |
| `VDSync` | 2 |

| `Operation` | value |
|---|---|
| `Upsert` | 0 |
| `Delete` | 1 |

| union | members (value) |
|---|---|
| `SessionPayload` | `SyncData` (1), `Cleans` (2), `ChecksumModule` (3) |
| `MessageType` | `DataValue` (1), `DataClean` (2), `ChecksumModule` (3), `Start` (4), `DataContext` (5), `FullSession` (6) |

`Option` selects the vulnerability-detection treatment of a `SyncData` session: `Sync` skips the
scanner; `VDFirst` (an agent's first synchronization) and `VDSync` (subsequent deltas) run the
scan synchronously before indexing.

## Validity

The `mode` × `payload` matrix, request-level shape rules and per-mode semantics are documented in
the [API Reference](api-reference.md); everything outside the matrix is answered `400` before any
I/O happens. There is deliberately no `ModuleFull` mode: a full resync is composed by the agent
as two ordinary requests — a `Cleans` of the module's indices followed by a `ModuleDelta` with
the complete dataset — so the server has no special case for it.
