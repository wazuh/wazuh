# Release notes

## Highlights

- New Engine replacing `analysisd`, with YAML-based decoders, KVDB lookups, and event enrichment (IOC matching, GeoIP, filters).
- Native event forwarding to the Wazuh Indexer through the `indexer-connector` module; Filebeat is no longer required.
- Cluster-by-default deployment model: every Wazuh Server installation runs as a cluster node, removing the distinction between clustered and non-clustered deployments.
- Complete Agent/Manager separation: the Agent and Manager are now fully independent products with distinct installation paths, system users (`wazuh` vs. `wazuh-manager`), configuration files, daemon names, and runtime artifacts. Both can be installed and run simultaneously on the same host without conflicts, and all coupling through the reserved agent ID `000` has been removed. This applies to 5.x packages only: Wazuh 4.x agent packages declare a conflict with the `wazuh-manager` package, so the package manager will not install a 4.x agent package and a 5.x manager on the same host.
- New stateless event model: a 5.x agent sends lean events in a batch headed by its own metadata line (agent identity, groups, host), which `remoted` checks against the authenticated agent and forwards verbatim; the Engine parses that header once per agent and stamps it into every event, so every event reaching the Indexer carries the same metadata schema and `wazuh-db` is out of the ingestion hot path. On the legacy channel, `remoted` enriches the 4.x agent's events itself.
- New state synchronization model: agents own and persist their module state (FIM, System Inventory, SCA) locally and reconcile it with the Manager through a dedicated synchronization protocol with deterministic versioning and checksum-based recovery, replacing the legacy `rsync` path and reducing network traffic and server-side processing.
- Vulnerability Detection now uses the Wazuh Indexer as the authoritative CVE data source, fed by the CTI service, with CVSS v4.0 support.
- New RBAC actions for secrets and enrollment tokens: `agent:read_secrets` (exporting an agent's key) and `cluster:read_secrets` (the enrollment password and the cluster key in clear), both granted by the new default policy `secrets_read`, which only the `administrator` role holds; and `enrollment_token:create`, `read` and `delete`.
- Engine metrics collection, normalization, and indexing pipeline for internal observability.
- Configurable byte limits on the queues of `remoted`, the Engine, `indexer-connector` and the Inventory Sync Server, and a limit on pending on-demand vulnerability scans, bounding memory use under load.

## Breaking changes

- No in-place upgrade from 4.x: Wazuh Manager 5.x packages refuse to install on a host with a 4.x (or earlier) manager, whether as an upgrade or beside it, and `install.sh` refuses to update one; a 4.x agent on the host does not block the manager's own check. A fresh install plus the documented migration process is required.
- As part of Agent/Manager separation, the installation path moved from `/var/ossec` to `/var/wazuh-manager` and the configuration files to `/etc/wazuh-manager`; `ossec.conf` → `wazuh-manager.conf`, the XML root `<ossec_config>` → `<wazuh_config>`, `internal_options.conf` → `wazuh-manager-internal-options.conf`, `ossec.log` → `wazuh-manager.log`, the system user/group `wazuh` → `wazuh-manager`, and the control binary and daemons were prefixed accordingly (`wazuh-control` → `wazuh-manager-control`, `wazuh-analysisd` → `wazuh-manager-analysisd`, and so on; the `wazuh-manager.service` systemd unit name is unchanged). Any automation or tooling referencing these paths, filenames, daemon names, or the system user must be updated.
- Filebeat was removed as the log-shipping component; event forwarding is configured in the manager's `<indexer>` section.
- The cluster is always enabled; the `cluster.disabled` configuration option was removed.
- Deprecated manager daemons were removed and are no longer shipped: `ossec-authd`, `wazuh-agentlessd`, `wazuh-maild`, `wazuh-dbd`, `wazuh-csyslogd`, `wazuh-integratord` and `wazuh-reportd`. The manager no longer runs `wazuh-logcollector`, `wazuh-syscheckd` or `wazuh-execd` either: its daemons are `wazuh-manager-clusterd`, `-modulesd`, `-remoted`, `-analysisd`, `-db`, `-authd` and `-apid`.
- The deprecated CLI tools `manage_agents` and `agent-auth` were removed from the manager. `manage_agents` is still shipped with the agent, and agents enroll with the agent's own `wazuh-agent-auth`.
- `wazuh-manager-authd` no longer replaces an existing agent when a registration names the agent ID explicitly (`POST /agents/insert`). The request is rejected instead: `1708` when the ID belongs to an existing agent, and the new `1763` when the ID's previous owner still has documents pending deletion in the Indexer. Reusing an ID requires deleting the agent and letting its deletion complete. `<force>` is unaffected for enrollments that do not name an ID — those keep replacing by name or IP, and the replacing agent receives a new ID, as before.
- Agent deletion no longer purges the Indexer synchronously: the deletion of the key, the wazuh-db row and the Indexer documents are now decoupled. The Indexer purge becomes a durable Task Manager task, first attempted after the `authd.purge_delay` internal option's seconds (default `120`) and retried until it succeeds, so an Indexer outage delays a deletion rather than losing it. `DELETE /agents` therefore returns before the documents are gone; tooling that deletes an agent and immediately asserts on the Indexer has to wait. A deletion can now also be **refused** with the new `1766` when too many earlier ones are still pending — the agent is left untouched and the request can be retried once the backlog drains. An automatically assigned agent ID is never one a deleted agent held, so the IDs handed out after a deletion may skip values.
- `<global><agents_disconnection_alert_time>` was removed, and a configuration still carrying it fails to start — `<global>` now accepts `<agents_disconnection_time>` alone. It delayed the agent-disconnection *alert* while a flapping agent still had a chance to come back, but alert emission to `analysisd` was already removed in 5.0, so it controlled only the timing of a debug log line, and its last consumer went with `wazuh-manager-monitord`. Agents are still marked `disconnected` after `<agents_disconnection_time>` with no delay, which is what this option never gated. `remoted`'s active-configuration report no longer includes the field.
- An internal option written with no value (`remoted.debug=`, or with only spaces) now refuses the daemon's start. It used to be read as `0`, which passed the range check on every option whose minimum is `0` and failed it on the rest, so the same unfinished edit either started the daemon with a value nobody chose or stopped it, depending on which option it was. An option that is absent still falls back to its default. Applies to every daemon, on the manager (`wazuh-manager-internal-options.conf`) and on the agent (`internal_options.conf` and `local_internal_options.conf`).
- The `wazuh-manager-monitord` daemon was removed, and its periodic work moved into the Task Manager inside `wazuh-manager-modulesd`: the agent disconnection sweep, the disconnection log line, the retention deletion of long-disconnected agents (`monitord.delete_old_agents`) and both daily and size-based log rotation. Every option keeps its meaning, range and default, and no new `<task-manager>` configuration is introduced, but the manager's internal options **moved from the `monitord.` namespace to `wazuh_modules.manager_task_*`** (for example `monitord.rotate_log` → `wazuh_modules.manager_task_log_rotate`; the full table is in the manager configuration migration guide). An override left under the old name is silently ignored, so rename any you had set in `wazuh-manager-internal-options.conf`. Agents are unaffected and keep `monitord.*` for their own log rotation. Because these options have no XML element, the values a running manager resolved are reported by `GET /cluster/{node_id}/configuration/wmodules/wmodules` under the `task-manager` module's `recurring_tasks` object. **The `monitor` component of the active-configuration endpoints is gone**, since it was served by monitord's own `getconfig` socket: `GET /cluster/{node_id}/configuration/monitor/{global,internal}` now returns `400`. It only ever returned monitord's own internal options, and the Task Manager exposes no `getconfig` endpoint, so there is no replacement request. Four behaviours also change: the disconnection sweep no longer runs on cluster workers (it did, despite the flag that was meant to prevent it, and a cluster stanza that fails to parse is now treated as "not the master" instead of silently as master); daily rotation now fires after a same-day restart, where the previous implementation re-seeded its day baseline on every start and so never rotated on a manager restarted daily; size-based rotation is checked once a minute rather than once a second; and the two agent sweeps no longer poll on the same value they apply as a threshold, so an agent is marked `disconnected` between `<global><agents_disconnection_time>` and that value plus one poll — 15 to 18 m 45 s at the default, where monitord delivered 15 to 30 minutes because its sweep period *was* the threshold. Scheduled runs (the two sweeps and daily rotation) are now durable, retried and queryable per schedule instead of living in process memory; the size check keeps no task record. Tooling that lists manager daemons must drop `wazuh-manager-monitord`. See [Recurring manager tasks](modules/task_manager/schedules.md).
- `wazuh-manager-authd`'s TLS enrollment listener (port 1515, used only by 4.x agents) now enforces TLS 1.3 as the minimum protocol version and rejects TLS 1.2 or older handshakes; the `auth.ssl_auto_negotiate` configuration option and the `-a` CLI flag were removed, and `<auth><ciphers>` now expects a TLS 1.3 ciphersuite list instead of an OpenSSL cipher-list string. On the agent, `<enrollment><ssl_cipher>` (superseded by `<agent><ssl>`) and `<enrollment><auto_method>` are no longer used: a configuration carrying them still starts, and each is logged at `INFO` and ignored.
- Syslog remote input (`remoted` `syslog` connection mode, port 514) was removed.
- Ruleset migration: the Engine replaces `analysisd` and its ruleset format — XML decoders are replaced by YAML decoders, and CDB lists are replaced by KVDB key-value databases.
- The Vulnerability Detector offline feed was removed. CVE data is now distributed through Wazuh CTI into the Wazuh Indexer, and the Manager downloads it from the Indexer. Air-gapped deployments must provide access to an Indexer whose CTI consumer has been populated; custom/offline feed sources are no longer supported.
- Agent metadata in Vulnerability Detection documents moved to `wazuh.agent.*` (the agent's host details under `wazuh.agent.host.*`); `host.os.*` describes the scanned operating system. Custom dashboards, queries, and integrations targeting the previous field paths must be updated.
- Threat-related fields were aligned under the `wazuh` namespace in the Engine enrichment; queries and dashboards referencing the previous threat field locations must be updated.
- The VirusTotal integration was removed along with `integratord`. Real-time VirusTotal lookups have no direct replacement; IOC-based enrichment is now handled inline by the Engine against the Wazuh IOC database. Existing `integratord`-based VirusTotal configurations no longer apply.
- Active Response was redesigned around the Wazuh Indexer Alerting/Notifications plugins (new `active_response` channel type): the manager `ar.conf` file and the `<active-response>` and `<command>` configuration blocks were removed, and the `PUT /active-response` API endpoint was removed.
- The server-side OpenSCAP module was removed; use SCA instead.
- Inventory-related API endpoints (`/syscollector`) were removed.
- Manager index names changed: the Engine indexes events into `wazuh-events-v5-<category>`, and the state indices no longer end in the cluster name (`wazuh-states-vulnerabilities`, `wazuh-states-inventory-<type>`, `wazuh-states-fim-<type>`); SCA state is new, in `wazuh-states-sca`.
- Rootcheck server-side simplification: the manager-side rootcheck database, synchronization path, and read-only API were removed; the agent reports its findings statelessly, with no manager-side storage.
