Brief — what issue #37396 is actually about (no Wazuh knowledge assumed)

The 30-second version

Wazuh is an open-source security platform: a central server collects security telemetry from agents installed on endpoints (servers, VMs, cloud nodes). On Linux, the agent can use eBPF — a kernel technology that runs small, safe programs inside the Linux kernel to observe events like "a file was opened", "a process started", "a network connection was made" — as a high-quality, low-overhead event source.

Today, the agent's eBPF machinery is not a standalone component: it is embedded inside one consumer (File Integrity Monitoring). Wazuh is building container runtime security (parent objective #37203), and several features now need the same kernel event stream at once. This spike (#37396) researches how to pull the eBPF engine out into its own module — one owner of the kernel programs and the event pipe, with multiple subscriber modules — and, inseparably, what kernels/container runtimes that module can actually support, because you cannot design the module's interface and degradation behavior without knowing the compatibility floor.

It is a *spike* (type/research): the deliverable is understanding — decision records, an event contract, a compatibility matrix, a prototype proving the design — not shipped product code.

The cast of characters

  • Wazuh agent — the program on each monitored machine. On Linux it runs as a systemd service on the host ("host package"). That detail matters: privilege analysis is about a host process, not a Kubernetes pod (issue: Background, last paragraph).
  • FIM (File Integrity Monitoring, historically "syscheck") — the agent feature that detects file changes. Its "who-data" mode records *who* touched the file, and on modern Linux that is powered by eBPF. This is where the eBPF engine lives today. (Confirmed by code audit — see code-map.html.)
  • IT Hygiene (historically "Syscollector" / inventory) — the agent feature that inventories the system: packages, processes, ports, network config. #37203 makes it a first-class eBPF consumer too (process-exec + network events), not just FIM.
  • Container Instances Security Module — a *new* module (separate spike) that talks to Docker/Kubernetes APIs and knows which container/pod/label corresponds to which cgroup/PID. Deliberately passive: it enriches; it does not produce runtime events.
  • eBPF Module — the thing this spike designs. Sole producer of low-level runtime events; owns BPF program lifecycle, the ring buffer (the kernel→userspace event queue), and delivery to subscribers.

Anatomy: what "an eBPF program" actually is, and what the tree contains

eBPF is not just an API. It is three things bundled: a tiny virtual machine inside the kernel that executes sandboxed bytecode; a verifier that proves each piece of bytecode safe (bounded, memory-safe) before it may run; and an API surface (the bpf() syscall plus "helpers" — the short list of kernel functions the bytecode may call). The key inversion vs a normal API: you don't call the kernel and get data back — the kernel calls your code, inside itself, at the exact moment an event happens. That is why eBPF catches short-lived activity and can stamp correlation keys at event time.

In eBPF-speak, a "program" is one small function attached to one hook — tens of lines of restricted C (no unbounded loops, tiny stack, whitelisted helpers only), not an application. FIM is therefore NOT an eBPF program and never could be; FIM uses eBPF through three distinct artifacts in the codebase:

  • The ten eBPF programs — src/syscheckd/src/ebpf/src/modern.bpf.c (one 984-line file): 4 kprobe programs + 6 LSM-hook programs (3 hooks × dpath/walk variants). Each fires in-kernel for microseconds: read pid/uid/path from kernel structs → copy a file_event into the ring buffer → done. Clang compiles the file to bytecode (modern.bpf.o) which ships with the agent as a data file, loaded into the kernel at runtime — it is not part of any executable.
  • The engine (userspace) — ebpf_whodata.cpp → libfimebpf.so, normal C++ linked into the FIM daemon: loads the bytecode via libbpf (the verifier checks each program), picks the LSM or kprobe set, attaches, then reads events off the ring buffer for the daemon's lifetime.
  • FIM proper — the big userspace daemon (wazuh-syscheckd) that consumes the events and applies file-integrity logic.

Analogy: the BPF programs are tripwire sensors screwed into the kernel's walls; the engine is the wiring and receiver box; FIM is the alarm control panel. This spike turns the sensors + wiring into shared building infrastructure (the eBPF Module, with more sensor types: exec + network) instead of hardware the alarm panel privately owns — FIM then just subscribes like any other consumer.

Why now (the driver)

Parent #37203 wants container-aware security: when a file inside a container changes, FIM should say *which container/pod/image*. The chosen architecture (its NFR4 + implementation restrictions 1-2) is:

kernel events → eBPF Module → (raw events + correlation keys) → FIM / IT Hygiene
                                                        ↓ (query, enrich)
                                     Container Instances Security Module

The eBPF Module must emit events carrying correlation keys (PID, cgroup id, namespace inodes, container id where derivable) so consumers can ask the Container module "whose cgroup is this?" — while the eBPF Module itself stays ignorant of containers. That keeps the modules decoupled: the engine produces; the container module explains; FIM/IT Hygiene decide.

The two halves of the spike

  1. Module design — is the module an in-process library, a thread pool, or a separate process? What exactly is the event schema and the subscribe/filter API? How does it load, attach, detach, and survive config reloads? What happens when the buffer overflows or one subscriber is slow? Prove extensibility: a third consumer must plug in without touching the engine; the same engine must serve plain hosts with no containers at all.
  2. Kernel/runtime compatibility — Wazuh supports old enterprise kernels (RHEL 8 = 4.18) through new ones (Ubuntu 24.04 = 6.8). Modern eBPF niceties (LSM hooks, bpf_d_path, ring buffer) don't exist on the old end. The spike must decide the minimum kernel per event class, the attach mechanism + fallback (LSM vs kprobe/tracepoint), how containerd/CRI-O/Docker and cgroup v1/v2 affect the correlation keys, what Linux capabilities the host service needs (CAP_BPF, CAP_PERFMON, …), and a performance budget.

They are one spike because the contract you can promise depends on the features you can rely on.

What "done" looks like

Event contract accepted by the FIM and IT Hygiene spike owners; architecture + min-kernel decisions committed as ADRs; compatibility matrix signed off by platform/QA; a working prototype of two independent subscribers with different filters over one stream — on one modern (LSM) and one old (kprobe/tracepoint) kernel; correlation keys aligned with the Container module spike. (Full checklists: requirements.html.)

Hard constraints to keep in mind

  • No new external dependencies; C/C++ only; BPF loading via what's already vendored.
  • Protobuf is explicitly disallowed for the wire format.
  • Consumers must not contain eBPF-specific code beyond the subscription.
  • The engine must never depend on the Container module (direction of knowledge is one-way).
