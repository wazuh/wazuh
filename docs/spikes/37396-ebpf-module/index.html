In one paragraph (no Wazuh assumed)

Wazuh is an open-source security platform: agents on endpoints send security telemetry to a central server. On Linux, the agent already uses eBPF — small verified programs running inside the kernel — to watch file activity, but that machinery is welded into one feature (File Integrity Monitoring's "who changed this file" mode). Wazuh is now building container runtime security (parent objective #37203), where several features need the same kernel event stream at once: file changes for FIM, process starts and network connections for the IT Hygiene inventory. This spike researches two inseparable things: how to carve the eBPF engine out into its own module (one owner of the BPF programs and the event pipe, many subscribers, each event carrying "correlation keys" so consumers can map it to a container), and what kernels and container runtimes that module can honestly support — because the interface you can promise depends on the kernel features you can rely on, and Wazuh supports enterprise kernels as old as RHEL 8's 4.18. It is a research issue: the outputs are decision records, an event contract, a compatibility matrix, and a proof-of-concept — not shipped product code.

Introduction — the world this issue lives in

The platform, in three sentences

A Wazuh agent is installed on each monitored machine (server, VM, cloud node) and reports to a central Wazuh server, which analyzes events, stores state in an indexer (OpenSearch), and renders a dashboard. On Linux the agent is a set of cooperating daemons run as systemd services on the host — a "host package", not a container — which matters later for privileges (issue, Background). The agent code lives in this repo; branch main is 5.1.0-alpha0 (VERSION.json), exactly the version this issue targets.

eBPF (the technology)

A Linux kernel facility that runs small, statically-verified programs inside the kernel, attached to events: function entries (kprobes), stable trace points, or security hooks (LSM). Programs push records to user space through a shared ring buffer. No kernel module, no reboot.

ebpf.io · docs.kernel.org/bpf

FIM — File Integrity Monitoring

The agent feature (daemon wazuh-syscheckd, historically "syscheck") that detects file changes. Its whodata mode adds who made the change — backed on Linux by either the Linux Audit subsystem or, since 4.8/4.9, eBPF. That eBPF backend is the engine this spike extracts.

src/syscheckd/ · docs: FIM advanced settings

IT Hygiene — Syscollector

The agent's inventory feature (5.x name "IT Hygiene", module name syscollector): packages, processes, ports, network interfaces. The parent objective promotes it to a second eBPF consumer — it wants process-exec and network events, which the current engine does not produce at all.

src/wazuh_modules/syscollector/ · #37203 FR7

The module framework

Most agent features run as "modules" inside the wazuh-modulesd daemon: a linked list of wm_context structs (name/start/stop/query…), one thread each. 5.x collectors (Syscollector, SCA) are C++ engines in shared libraries behind thin C wrappers. FIM is the exception — still its own daemon.

wmodules_def.h:35-43 · evidence/module-framework.html

Container Instances Security Module

A planned module (sibling spike #37382) that talks to Kubernetes/Docker APIs and answers "this cgroup id = that container/pod/image/labels". Deliberately passive: consumers query it to enrich events; it never touches the event stream and must never be a dependency of the eBPF Module.

#37203 Description, IR1 · evidence/siblings.html

Correlation keys

The raw identifiers an eBPF event must carry so a consumer can later ask "which container did this?": PID, cgroup id, namespace inode numbers, container id where derivable. The kernel knows these at event time; container names/images it does not — that mapping is the Container module's job.

#37203 FR6 · issue angle 3

Why this spike exists

The parent objective's architecture (its NFR4 and implementation restrictions 1–2) splits responsibilities: the eBPF Module produces raw runtime events; FIM and IT Hygiene consume and independently enrich them via the Container module; enriched state flows to the server over the existing state-sync infrastructure. Today's reality is far from that: the engine is embedded in FIM, speaks FIM's structs, filters with FIM's config, produces file events only, and collects zero container-correlation data. The spike designs the extraction and pins down the compatibility floor it can promise — in one issue, because the event contract, capabilities, and degradation behavior "can only be designed against a concrete compatibility floor" (issue, Background).

The ask, dissected

The issue is two tightly-coupled research tracks. Everything below is a restructuring of the issue body; nothing is invented.

Track 1 — Module design

Boundary: in-process library vs dedicated threads vs separate process — trade privilege isolation (BPF needs strong capabilities) against IPC cost and restart independence (angle 1).

Coupling audit: enumerate exactly what is FIM-specific today and must be cut or generalized (angle 2). → done, see "What exists in-tree".

Event contract (the core deliverable): schema per event — type, timestamp, PID/TID, path, and the correlation keys; versioned; serialization is hand-rolled flat layout, protobuf disallowed (angle 3).

Subscription & filtering: how consumers register interest (event types, path prefixes, per-cgroup scope); what filtering can be pushed into the kernel (angle 4); one program with user-space demux vs per-consumer programs.

Lifecycle: load/attach on start, clean detach, re-attach on config change without dropping events for other consumers; graceful degradation when capabilities/kernel features are missing (angle 5).

Backpressure: ring buffer sizing, drop policy, drop surfacing (a silently dropped event is a missed security state), slow-consumer isolation (angle 6).

Extensibility proof: adding a 3rd consumer must not touch the engine; the same engine must serve plain hosts with empty correlation keys (angle 7).

Track 2 — Kernel / runtime compatibility

Kernel floor: which eBPF features each event class needs; single attach mechanism or fallback for old kernels; explicit policy question — lowest common denominator vs higher floor with documented exclusions (angle 8).

Features per event class: file = LSM hooks vs kprobes + path resolution; exec = sched_process_exec tracepoint / exec kprobes + argv; network = socket kprobes/fentry + cgroup association; cross-cutting = CO-RE/BTF, ring buffer vs perf-array, cgroup-id and namespace helpers (angle 9).

Attach decision: LSM-only vs kprobe/tracepoint fallback — compare event QUALITY (false positives, missed events) and the maintenance burden of two attach paths (angle 10).

Container runtimes: containerd, CRI-O, Docker — do hooks fire identically, are cgroup/namespace semantics consistent (angle 11)? cgroup v2 unified vs hybrid v1; systemd vs cgroupfs driver (angle 12).

Host privileges: capabilities for a systemd service (CAP_BPF, CAP_PERFMON, CAP_SYS_ADMIN, CAP_DAC_READ_SEARCH), SELinux/AppArmor policy deltas the package must ship or document (angle 13).

Performance budget: events/sec on a busy node across all three classes, absorbable per-event cost, kernel-side vs user-space filtering (angle 14).

Explicitly out of scope: the container→pod/metadata resolution algorithm and file-path resolution — those belong to sibling spikes #37382 (Container module) and #37533 (FIM integration). The engine only ships raw keys.

Hard constraints (issue, Constraints)

  • No external dependencies, feature-wide: C/C++ on the stack Wazuh already ships; BPF loading via what is already vendored (libbpf — confirmed in-tree via libbpf-bootstrap); no new runtime SDKs.
  • Consumer-agnostic: FIM/IT Hygiene must need nothing eBPF-specific beyond subscribing; a third consumer must never require touching the engine.
  • Events carry enough raw identity that consumers can correlate to containers without the eBPF Module ever depending on the Container module.
  • Serialization: hand-rolled/flat layout; protobuf explicitly disallowed (angle 3).

What exists in-tree today (audited, verified)

Everything eBPF lives in one directory — src/syscheckd/src/ebpf/ — building one shared library (libfimebpf.so) used by exactly one consumer: FIM's whodata mode. Physically easy to lift; logically fused to FIM at three seams:

The engine filters with FIM's config. The ring-buffer callback looks the path up in FIM's directory table and drops the event unless that directory has WHODATA_ACTIVE — FIM's monitoring semantics are hardcoded inside the engine.

The engine emits FIM's struct. Events leave as whodata_evt — FIM's own type (syscheck-config.h:228-252) — built field-by-field in the engine and pushed through a FIM callback.

ebpf_whodata.cpp:670-691

The engine runs on 9 FIM callbacks. Config lookup, user/group resolution, event delivery + free, logging, path absolutization, shutdown flag, queue size — all injected from FIM at init.

And where would a new module plug in?

The 5.x pattern for big collectors is: C++ engine as a shared library (src/wazuh_modules/<name>/) + thin C wrapper (wm_<name>.c) exposing a wm_context, hosted one-thread-each by wazuh-modulesd. But note: FIM is not hosted there — it is its own daemon that modulesd only queries over a socket, and today's engine lives inside that daemon. So "make it a module" has at least three structurally-precedented shapes (wmodule in modulesd / library linked into consumers / separate daemon), which is exactly the issue's angle 1 question. Registration recipe with file:line: evidence/module-framework.html §7. Also relevant: the repo has no ADR convention yet — design docs live in the mdBook at docs/ref/modules/<module>/architecture.md; the spike's "ADRs committed in the repo" will establish the convention (§8).

Compatibility — the landscape the design must survive

The real internal Tier 1/2/3 agent OS matrix was provided by the team (2026-07-13, evidence/tier-matrix.html) — it supersedes the issue's example distro list and reaches meaningfully lower (RHEL/CentOS 7, Amazon Linux 2, Debian 10) and higher (RHEL 10, Debian 13, Fedora 44, Ubuntu 26.04). Crossing it with the desk-verified feature floors (BCC kernel table + man pages, evidence/kernel-features.html) splits the Linux fleet into three bands. Kernel numbers are verified per distro docs; feature availability is still derivation, not probe results — RHEL backports features into old version numbers and distro kernel configs vary, which is why the issue demands an empirical matrix (starting point 7).

Crash course — the eight terms the table below uses (plain English)

Each term answers one of five questions about running eBPF on a given machine:

Where can a program attach? kprobebreakpoint on almost any internal kernel function; works on ancient kernels, but kernel internals aren't a stable API — needs maintenance
tracepointofficial, maintained instrumentation points (e.g. "a process just executed"); stable, ancient
LSM hooksthe kernel's security checkpoints (where SELinux/AppArmor plug in) — the semantically correct spot for security events; BPF can attach only on kernel ≥5.7 AND if the machine opted in at boot (bpf in lsm=)
How does data get out? ring bufferthe modern kernel→userspace event queue (ordered, signals when full); exists only since kernel 5.8 — this is today's hard floor
What can the program read? bpf_d_pathhelper that turns an open file into its full path (/etc/passwd); ≥5.10, callable from LSM-type hooks only — without it the code walks the directory tree by hand
cgroup-id helperreturns the ID of the process's control group — THE "which container did this" correlation key; since 4.18 (AL2's 4.14 kernel lacks it)
What privileges are needed? CAP_BPF / CAP_PERFMONnarrow root-powers ("capabilities") covering just BPF, since 5.8; older kernels force CAP_SYS_ADMIN — "basically root". Nuance: the hosting daemons (modulesd, syscheckd) already run as root (only agentd drops to the wazuh user — verified in each main.c), so this row is about hardening/confinement options and SELinux/AppArmor policy (which can deny bpf() even to root — see the installer's chcon), not about making it work
Does one binary run everywhere? BTF / CO-REBTF = metadata a kernel publishes about its own structs; CO-RE = our pre-compiled program adapts itself to the running kernel by reading its BTF at load time. Kernels built without BTF (Debian 10, Ubuntu 20.04-GA, AL2-4.14) can't run our one-binary build — we'd have to ship metadata or per-kernel builds

How can ONE module work across such different kernels? Four mechanisms, all already proven in-tree at small scale: (1) probe, don't assume — a startup healthcheck loads programs and round-trips a real event; on failure the module declares itself unavailable instead of limping (ebpf_whodata.cpp:715-798 → syscheck.c:827-831); (2) CO-RE — one compiled BPF object relocates itself against the running kernel's type info at load time, which is how today's single modern.bpf.o spans 5.8→6.x unmodified; (3) graded program sets — the same event can be acquired via LSM+bpf_d_path, LSM+path-walk, or plain kprobes, selected at startup per box (ebpf_whodata.cpp:482-525); consumers always see the same event, never the hook; (4) a floor — below ≥5.8 the module refuses cleanly and those boxes keep today's behavior (audit whodata for FIM), as a documented product exclusion. Like SIMD dispatch in a library: one binary, runtime feature probe, best path chosen, one API, documented minimum.
The central tension, sharpened by the tier table: today's engine floor is kernel ≥ 5.8 (ring buffer, enforced at ebpf_whodata.cpp:360) with Linux Audit as the fallback — but audit only replaces file events; there is no audit-equivalent for process-exec or network. A modern-first floor (≥5.8/5.10) covers 100% of Tier 1 Linux and most of Tier 2; paying the Band 1 tax (perf-event-array + kprobe-only + BTF strategy + CAP_SYS_ADMIN) buys essentially the RHEL 8 clone family plus aging editions (AL2 past upstream EOL with a 5.10 default anyway; Ubuntu 20.04 has HWE 5.15); and Band 0 (RHEL/CentOS 7) is unreachable no matter what. That is the kernel-floor decision (Q2) the spike must get product sign-off on — per event class, argued in tier+band terms.

Published docs today (4.14 — no 5.x docs exist) confirm the current world: eBPF is documented only for FIM whodata, "requires kernel version 5.8 or higher", falls back to audit, three file hooks. Details + verbatim quotes: evidence/docs-whodata.html.
