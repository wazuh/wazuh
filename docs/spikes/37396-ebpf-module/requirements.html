The ask (two tightly-coupled halves)

  1. Module design — boundaries, consumer-facing interface (subscription/event contract), process/threading + lifecycle model, correlation keys carried by raw events.
  2. Kernel / runtime compatibility — which kernels, eBPF features, container runtimes and cgroup layouts are supported; fallback story for older kernels. Lives in this spike because the event contract and degradation behavior can only be designed against a concrete compatibility floor.

Target topology (from issue Background):

  • eBPF Module — sole source of low-level runtime events (file, process-exec, network). Owns BPF programs, lifecycle, ring buffer, event delivery.
  • FIM & IT Hygiene — consumers; subscribe to raw events/state; independently query the Container Instances Security Module for enrichment.
  • Container Instances Security Module — passive enrichment source, NOT a producer.

Scope

In scope (design)

  • [ ] Module architecture: in-process library vs separate process/daemon
  • [ ] Public event contract
  • [ ] Subscription/filtering API
  • [ ] Program lifecycle (load/attach/detach on config change)
  • [ ] Fan-out to multiple consumers
  • [ ] Backpressure/overflow policy
  • [ ] Set of correlation identifiers emitted per event

In scope (compatibility)

  • [ ] Minimum kernel version + required eBPF features across Tier 1/2 Linux agents
  • [ ] Attach-mechanism decision (LSM vs kprobe/tracepoint) + older-kernel fallback
  • [ ] Hooks/helpers needed for file + process-exec + network events
  • [ ] Container-runtime compatibility (containerd, CRI-O, Docker)
  • [ ] cgroup v1/v2 behavior
  • [ ] Host-process capability requirements (agent = host systemd service, NOT a DaemonSet)
  • [ ] Performance budget

Out of scope

  • Container→pod/container metadata resolution algorithm and path resolution (→ Container Instances Security Module spike and FIM integration spike)

Constraints

  • No external dependencies (feature-wide): C/C++ on the stack Wazuh already ships; BPF loading via what Wazuh already uses ("libbpf/CO-RE if already vendored — confirm current state in-tree"); no new runtime SDKs.
  • Consumer-agnostic: FIM/IT Hygiene must not need eBPF-specific code beyond subscribing; adding a third consumer must not touch the engine.
  • Events carry enough raw identity for correlation without the eBPF Module depending on the Container Instances Security Module (preserves NFR4 decoupling).
  • Serialization: protobuf explicitly disallowed — hand-rolled/flat layout (issue, angle 3).

Deliverables

Module design

  • [ ] Module architecture decision record (in-process vs separate process, threading, capability confinement, mapping to agent module framework) with rationale
  • [ ] Coupling extraction map (current eBPF touch-points → target boundary; concrete refactor list)
  • [ ] Event contract specification (schema incl. correlation keys for file/exec/network, versioning, serialization, subscription/filter API)
  • [ ] Backpressure & degradation policy (ring buffer sizing, drop policy, drop surfacing, slow-consumer isolation, missing-feature behavior)
  • [ ] Extensibility proof (3rd-consumer sketch + host/no-container path)
  • [ ] Prototype: multi-consumer fan-out demonstrating decoupling

Kernel / runtime compatibility

  • [ ] Compatibility matrix — rows (distro, kernel, runtime, cgroup mode, cgroup driver) × columns (LSM attaches?, kprobe/tracepoint attaches?, ringbuf works?, bpf_d_path correct?, bpf_get_current_cgroup_id correct?, file/exec/network events?, perf category)
  • [ ] Min-kernel decision record (per event class, with product sign-off)
  • [ ] Host-capability requirements + SELinux/AppArmor policy delta for the package
  • [ ] Performance numbers (sustained events/sec ×3 classes, p99 BPF runtime, drop rate at saturation)

Acceptance criteria

  • [ ] Event contract reviewed & accepted by BOTH the FIM and IT Hygiene integration spike owners, covering file + process-exec + network events
  • [ ] Architecture decision and min-kernel decision committed as ADRs in the repo
  • [ ] Compatibility matrix signed off by platform/QA; kernel floor per event class feeds objective restriction #4 ("supported agent platforms to be defined")
  • [ ] Coupling extraction map cross-referenced by the implementation tickets
  • [ ] Prototype: two independent consumers, distinct filters, one event stream, each receiving correlation keys, no consumer can stall the other, on ≥1 LSM-capable kernel AND ≥1 kprobe/tracepoint-fallback kernel
  • [ ] Correlation-key set aligned with the Container Instances Security Module spike findings (PID/cgroup/namespace/container id)
