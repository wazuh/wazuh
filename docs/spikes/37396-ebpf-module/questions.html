  • D3 (was Q3). Module boundary — ⚠ REOPENED 2026-07-15; no decision stands. Original call (2026-07-13, grilling — judged rushed by jr0me): modulesd-hosted C++ module with a socket-only subscription API; library-per-consumer rejected on the assumption it must duplicate identical BPF programs/ring buffers. Challenge (teammate via jr0me, 2026-07-15): make the engine a component (shared library) FIM/Syscollector instantiate independently — valid iff instances don't conflict at kernel level. Verified kernel facts: separate loads create fully independent programs/maps/ring buffers (no conflict; hooks accept multiple attached programs; kernel auto-detaches on fd close); and a ring buffer has a single consumer cursor, so two processes can never read one ring buffer — per-consumer instances and one-owner-fan-out are the only two possible shapes. Decisive v1 observation: FIM (file) and IT Hygiene (exec+network) need disjoint event classes, so per-consumer instances duplicate almost nothing today; the component model also gets slow-consumer isolation by construction and matches the shared_modules precedent (dbsync, agent_sync_protocol). Costs: hot-path cost multiplies if future consumers overlap classes; possible LSM/kprobe mode divergence between instances on one box; N lifecycles/healthchecks; tension with NFR4's literal "sole source" and AC-5's "one event stream" wording (needs issue-owner buy-in to reframe). Status (jr0me): "I cannot make this decision now, the previous call seems rushed; modify D3 to evaluate all options with pros/cons." → The architecture ADR (P1.3) is now a full multi-option evaluation: (a) component/shared library with per-consumer instances, (b) modulesd-hosted module + socket fan-out, (c) dedicated daemon (wazuh-ebpfd). Decision fulcrum: the class-overlap question + NFR4 wording alignment. Tracked as open item O5.
