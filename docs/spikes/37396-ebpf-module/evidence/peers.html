Evidence — peer-pattern survey: Tetragon, Falco, Inspektor Gadget, Hubble

Issue starting point 2 ("survey peers for the shared eBPF provider pattern — extract the interface patterns, not the code"). Documentation-level survey via two research agents, 2026-07-15; load-bearing kernel-floor and architecture claims spot-checked by hand against the cited pages. Where public docs are silent, items say NOT DOCUMENTED.

The headline for our boundary question (O5)

The four peers cover our entire option space, and none of them does the one thing our reopened D3 debate implicitly asked about: no project shares one loaded BPF program set across independent processes. The industry's answers really are the two shapes our ring-buffer analysis predicted — per-consumer instances or one-owner fan-out.

Second decisive input: Falco tried and retired the "embedded gRPC event subscription server" — deprecated in 0.43 because it "add[s] substantial complexity to the core codebase, including dependencies on specific protobuf and gRPC framework versions" (falco.org/blog/falco-0-43-0). A warning label for our socket-fan-out option, though our constraint set differs (hand-rolled flat format, no protobuf, local socket only).

Tetragon (Cilium) — the dedicated-daemon archetype

  • Shape: per-node daemon (DaemonSet/container/systemd package) exclusively owning all BPF programs; consumers subscribe over gRPC server-streaming (GetEvents, default unix socket). Program bundles ("sensors") load/unload at runtime via the same gRPC surface (AddTracingPolicy…) — lifecycle without restart. Multiple listeners each get their own buffer; a slow listener overflows alone (tetragon_notify_overflowed_events_total: "events dropped because listener buffer was full"). tetragon.io/docs/overview, /concepts/events, /reference/grpc-api, /reference/metrics
  • Contract: protobuf, shipped as an independently versioned Go module (api/v1/tetragon). Every event carries identity resolved IN the daemon: cluster-unique exec_id, pid/uid, binary+args, container id (first 15 digits), pod metadata, namespaces, credentials — all subscribers see identical identity. Formal deprecation policy NOT DOCUMENTED. tetragon.io/docs/reference/grpc-api
  • Filtering: two layers. Kernel-side TracingPolicy selectors evaluated in BPF (matchArgs/matchBinaries/matchNamespaces/matchCapabilities…, K8s pod/namespace scoping via cgroup state populated by OCI hooks "before containers start executing", even in-kernel rate-limited Post); hard limits (≤5 selectors/hook). Userspace per-subscriber allow/deny lists + CEL expressions on the gRPC request. tetragon.io/docs/concepts/tracing-policy/*
  • Drops: counted at every stage with distinct metrics (bpf_missed → ringbuf lost → queue lost → per-listener overflow → export rate-limit) — but NO in-stream loss notification to gRPC consumers (metrics only). Community reports buffer tuning is opaque ("sometimes… can even make things worse", tetragon#4821). tetragon.io/docs/reference/metrics; github.com/cilium/tetragon/issues/4821
  • Kernel compat (verified): "needs Linux kernel version 4.19 or greater", tested on 4.19/5.4/5.10/5.15; BTF/CO-RE mandatory (CONFIG_DEBUG_INFO_BTF=y; BTFhub/pahole/rebuild as escape hatches). No attach-type auto-fallback: policies fail to load if the hook type is unavailable; features gate per kernel (kprobe arg resolution ≥5.4, LSM ≥5.7 + lsm=…,bpf). RHEL 8 @4.18: below floor, NOT in test matrix. tetragon.io/docs/installation/faq (spot-checked)

Falco — a 10-year experiment across all three options, regrets documented

  • Shape: layered libraries — drivers (kmod / eBPF) → libscap (reads ring buffers, OS state) → libsinsp (enrichment, state table, rule engine) — that each consumer process instantiates (CNCF-donated precisely for reuse; Stratoshark is another consumer). The modern CO-RE probe is embedded in the consumer binary ("a unique, self-contained executable"). Cross-process sharing of one driver's stream: NOT DOCUMENTED — their answer to multi-consumer is in-process plugins (trusted .so, "could crash the program"). Daemon fan-out is alerts only (stdout/file/HTTP + Falcosidekick), never raw kernel telemetry. github.com/falcosecurity/libs; falco.org/docs/concepts/plugins/architecture, /concepts/outputs
  • Contract: kernel→user is a raw C-struct format (ppm_evt_hdr + length-prefixed params) with two-axis version negotiation at startup: an API version (transport) and a Schema version (event types/fields) — the most directly relevant versioning pattern for our flat-format constraint. Userspace: sinsp field model; plugin ABI is semver'd (framework refuses mismatched major). falco.org/docs/concepts/event-sources/kernel/architecture
  • Enrichment placement (their 0.41 lesson = our architecture validated): container metadata enrichment was MOVED OUT of the core libs into an async plugin because doing it synchronously in-core raced container startup and lost metadata; the plugin pre-fetches on container-create ("onCreate comes way before onStart… plenty of time to deliver the container's metadata before the first process… is even started"). That is our parent's exact split (engine produces raw keys; a separate component enriches) and echoes #37532's replay-from-create idea. falco.org/blog/falco-0-41-0; github.com/falcosecurity/plugins (container)
  • Filtering: kernel-side = syscall-set pushdown computed from what consumers actually loaded ("union of the base set… and the syscalls specified in the loaded rules"), injected as a BPF map/bitmask, "ignore unnecessary syscalls before any data field extraction". Per-cgroup kernel scoping NOT DOCUMENTED (workload scoping is userspace rules). falco.org/blog/adaptive-syscalls-selection
  • Drops as consumer-visible POLICY: kernel drops-on-full with per-reason counters, and a configurable syscall_event_drops policy — actions [ignore|log|alert|exit], threshold, throttling — where the drop alert is delivered through the NORMAL event channel ("Falco internal: syscall event drop…"). The deprecated gRPC alert queue that grew "in memory until you read them" is their documented slow-consumer anti-pattern. falco.org/docs/concepts/event-sources/kernel/dropped-events
  • Kernel compat (verified) — degradation by ENGINE SWAP behind one capture interface: modern CO-RE probe (default; "usually all versions ≥5.8 are enough but… required features could also be backported", needs ring buffer + BTF; runs with just CAP_BPF, CAP_PERFMON, CAP_SYS_RESOURCE, CAP_SYS_PTRACE) ⇄ kernel module (≥3.10, "requires full privileges") for old fleets. The middle option — per-kernel-compiled eBPF probe — was their biggest operational pain ("a BPF probe for every supported kernel!") and was removed in 0.44; carrying two eBPF drivers "splits engineering effort" (0.43). falco.org/docs/concepts/event-sources/kernel (spot-checked); falco.org/blog/falco-modern-bpf, /falco-0-43-0, /falco-0-44-0

Inspektor Gadget — "library first, daemon as a thin host"

  • Shape: the engine is a supported Go library (GadgetContext + local or grpc runtime, operator pipeline); ig CLI, ig daemon (persistent detached "Gadget Instances"), and the K8s DaemonSet are thin hosts over the same library — Microsoft Defender for Containers embeds it in-process. Instrumentation ships as versioned OCI images (eBPF ELF + optional WASM + optional pre-generated BTF layer + metadata YAML). Per-instance model: each gadget run loads its own programs and declares its own buffer (GADGET_TRACER_MAP(events, 256KB)) — no shared event bus; only enrichment infrastructure (SocketEnricher, container collection) is shared engine state. Multi-client attach semantics to one instance: NOT DOCUMENTED. inspektor-gadget.io/docs (architecture, api/golang, spec/oci, headless)
  • Contract: no fixed global schema — per-gadget event structs, layout derived from BTF, transported as typed "data sources"; well-known field types (gadget_mntns_id, gadget_netns_id, timestamps, endpoints) TRIGGER enrichment/conversion by convention. Identity key = mount-namespace inode id resolved node-side to container/pod. Wire-format version negotiation NOT DOCUMENTED. inspektor-gadget.io/docs/gadget-devel/gadget-ebpf-api
  • Filtering: container scoping kernel-side via a mount-ns filter map (gadget_should_discard_mntns_id(), "as early as possible in the eBPF program"); generic field filtering userspace (Filter operator). inspektor-gadget.io/docs/gadget-devel/gadget-ebpf-api, /spec/operators
  • Drops — the audit lesson: a 2026 security audit found the fixed 256KB buffer dropped events SILENTLY — "an attacker could first produce many harmless events to flood the buffer, then perform malicious operations that would not be caught" — fixed by adding per-CPU _lost_samples counters reported to userspace. For a security product, an unsurfaced drop is a detection bypass, not an observability gap. shielder.com/blog/2026/04/inspektor-gadget-security-audit (spot-checked claim, kernel floor page verified)
  • Kernel compat (verified): "at least Linux 5.10 with BTF enabled"; optional btfgen OCI layer ships reduced BTF for BTF-less kernels (btfhub layout); and <gadget/buffer.h> auto-selects ring buffer (≥5.8) vs perf buffer — gadget code is transport-agnostic. The most reusable compat pattern if Band 1 is ever revisited. inspektor-gadget.io/docs/reference/requirements (spot-checked)

Hubble (Cilium) — the polished in-daemon hub

  • Shape (verified): "embedded into the Cilium agent in order to achieve high performance with low-overhead" — the agent owns the BPF datapath; Hubble owns no probes. Event path: BPF perf buffer → agent monitor → Hubble's lock-free userspace overwrite-ring (capacity 2ⁿ−1, default 4095) → per-subscriber "ring readers" with follow mode. Slow-client isolation is structural: the writer never blocks or tracks readers; a slow client is overtaken and gets a LostEvent — it can never stall the producer or peers. Cluster fan-out via a separate relay (mTLS, bounded sort buffer). docs.cilium.io/en/latest/internals/hubble (spot-checked)
  • Contract — loss is IN-BAND: one canonical protobuf Flow (identity pre-enriched server-side; "gRPC API is stable as of 1.0… upheld for the whole lifecycle of Cilium 1.x"), and the stream itself carries LostEvent{source, num_events_lost, cpu} with an enum naming WHICH stage dropped (PERF_EVENT_RING_BUFFER / OBSERVER_EVENTS_QUEUE / HUBBLE_RING_BUFFER), mirrored as hubble_lost_events_total metrics. Exactly the drop-surfacing shape #37532 asked us for. Pain points on record: false-positive loss metrics (cilium#46584), log spam under load (cilium#34981), user confusion (hubble#1737) — attribution must be precise per-stage/per-subscriber or it becomes noise. docs.cilium.io/_api/v1/flow; github issues cited
  • Filtering: per-subscriber server-side FlowFilters (allow/deny, pods, FQDNs, L7, CEL); kernel-side only global volume control (monitor-aggregation). No per-subscriber kernel predicates. docs.cilium.io/internals/hubble
  • Kernel compat: none of its own — inherits Cilium's (recommend "5.10 or later (or equivalent such as 4.18 on RHEL 8.10)", BTF required). Structural benefit of the hub model: consumers never care about kernels. docs.cilium.io/operations/system_requirements

Cross-cutting synthesis (our five questions)

QuestionConvergent industry answerDivergences that matter
(a) Boundary Nobody shares one loaded program set across independent processes; the real options are per-consumer instances (Falco libs, IG) vs one-owner fan-out (Tetragon, Hubble). IG dissolves the dichotomy: engine-as-library + daemon-as-thin-host over it. Falco retired its embedded gRPC event server for complexity; Hubble's works because it fans out one team's fixed schema.
(b) Contract Identity/correlation fields resolved once, node-side, before consumers see events; keys are kernel-native ids (mntns inode, cgroup/endpoint identity, container id). Schema shape splits: fixed protobuf (Tetragon, Hubble — one owner of vocabulary) vs per-source typed schemas + conventions (IG) vs raw structs with negotiated API+schema versions (Falco — closest to our no-protobuf flat-format constraint).
(c) Filtering Coarse scope filtering pushed into the kernel as early as possible (mntns/cgroup maps, syscall-set pushdown computed from consumer interest); fine per-consumer filtering in userspace (allow/deny + CEL). Nobody does per-subscriber kernel predicates. Tetragon uniquely does in-kernel rate limiting and enforcement actions.
(d) Backpressure Producer never blocks; drops counted at EVERY stage; slow consumers isolated (own buffer/cursor) and lose only their own events. All four learned drop-surfacing the hard way (IG audit; Hubble noise issues; Falco policy; Tetragon opaque tuning). Drop semantics: drop-newest (IG, Falco kernel-side, Tetragon) vs overwrite-oldest (Hubble ring). Surfacing: in-band on the stream (Hubble LostEvent; Falco self-alert through the normal channel) vs metrics-only (Tetragon).
(e) Kernel compat All are CO-RE-first with BTF required; practical floors 4.19–5.10; features gate per kernel rather than silently degrade. Old-fleet strategies: Falco = engine swap (kmod ≥3.10) behind one interface; IG = ship BTF in the artifact + auto ringbuf/perf switch; Tetragon = external BTF or unsupported. Falco killed per-kernel-compiled probes as unsustainable — the strongest external validation of our prebuilt-CO-RE + ≥5.8 floor direction (D2).

Direct inputs to our deliverables

  • → O5 / P1.3 (boundary ADR): the option space is fully represented in the wild; IG's layered pattern (library core, hosts as deployment choices) is the strongest candidate synthesis; Falco's plugin model shows in-process co-hosting works but couples crash domains; Falco's gRPC deprecation and Tetragon's buffer-tuning opacity are the recorded costs of the fan-out path; Falco-libs/IG per-instance duplication is the recorded cost of the component path (mitigated in our v1 by disjoint classes).
  • → P1.2 (contract): adopt Falco's two-axis versioning (transport API version vs event schema version) for our flat format; carry kernel-native correlation keys resolved once; adopt Hubble's in-band per-stage LostEvent + Falco's drop-policy actions as the drop-surfacing contract #37532 needs; per-consumer coarse scope filters kernel-side (cgroup/mntns maps), fine filters userspace.
  • → D-C3 (capabilities): Falco modern probe's documented minimum set (CAP_BPF, CAP_PERFMON, CAP_SYS_RESOURCE, CAP_SYS_PTRACE) is a concrete peer baseline for the systemd-unit analysis.
  • → D2 (floor ADR): peer floors (Tetragon 4.19-BTF-mandatory, Falco modern ≥5.8, IG 5.10) bracket our ≥5.8 recommendation; Falco's removal of per-kernel probes and "backported features" caveat both go into the rejected-LCD rationale.
