Evidence — what the public docs say eBPF does in Wazuh today

Source pages (fetched 2026-07-13; documentation.wazuh.com/current serves 4.14 — release notes top out at 4.14.6; there are NO published 5.x docs, and the spike targets 5.1.0):

  • https://documentation.wazuh.com/current/user-manual/capabilities/file-integrity/advanced-settings.html
  • https://documentation.wazuh.com/current/user-manual/reference/ossec-conf/syscheck.html

Findings

  1. Scope today: eBPF is used ONLY for FIM who-data (recording *who* changed a file), as an alternative to auditd. Verbatim: "Who-data monitoring in eBPF mode directly extracts FIM events from programs that use eBPF. This approach eliminates the need for external dependencies like auditd."
  2. Documented kernel floor: "Who-data monitoring with eBPF requires kernel version 5.8 or higher, as the data structure is only present in kernels starting with this version." (the data structure = the BPF ring buffer, mainlined in 5.8). No BTF/CO-RE requirement documented.
  3. Documented hooks (file events only, exactly three): vfs_open (file created…), security_inode_setattr (file modified), vfs_unlink (file removed); events cross to user space via "a kernel data structure called ring_buffer", consumed by the FIM module.
  4. Configuration: per-directory attribute whodata="yes" (default no) plus: ``xml <whodata> <provider>ebpf</provider> <!-- allowed: audit | ebpf; default audit --> <queue_size>50000</queue_size> <!-- larger = more agent memory --> </whodata> ``
  5. Fallback (verbatim): "If the <provider> tag is not configured, the FIM module defaults to the audit mode. Additionally, if the provider is set to ebpf, but unavailable due to kernel version incompatibility, it also falls back to the audit mode."
  6. Tier 1/2: not public terminology on docs. Closest: installation guide OS list and the packages list. GitHub issue wazuh/wazuh#31714 (closed) defines Tier 3 = AIX/Solaris/HP-UX removal and confirms tiers are an internal classification. ⇒ The distro/kernel table in #37396's body is the working assumption, not documented public fact. Superseded 2026-07-13: the real internal tier table was provided by jr0me — see tier-matrix.html; the issue's list is a subset of actual Tier 2.

Tensions to carry into the spike

  • Published floor is 5.8 + fall-back-to-audit; the spike contemplates distros *below* 5.8 (RHEL 8 = 4.18, Ubuntu 20.04 = 5.4) and an intra-eBPF fallback (LSM vs kprobe/tracepoint) — a different degradation model than today's documented one.
  • Today's documented eBPF surface = 3 file hooks for one consumer. The spike's surface = 3 event classes × multi-consumer fan-out ⇒ almost everything to be designed is net-new and publicly undocumented.
