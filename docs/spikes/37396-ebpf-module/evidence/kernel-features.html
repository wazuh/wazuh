Direct consequences for the spike

  1. Today's engine floor (ring buffer ⇒ 5.8, enforced at ebpf_whodata.cpp:360) already excludes RHEL 8 (4.18) and Ubuntu 20.04 (5.4) — currently those fall back to audit, a fallback that exists for file events only. There is no audit-equivalent for process-exec and network classes, so "what do old kernels get?" is a real product decision (issue angle 8).
  2. Supporting <5.8 within eBPF would require a perf-event-array path (not just kprobe-vs-LSM), which does not exist in-tree.
  3. bpf_d_path's hook allowlist couples the "nice path resolution" to the LSM/fentry attach path — on kprobe-only kernels the engine already falls back to manual dentry-walk (_walk variants), with the correctness caveats the issue asks to quantify (angle 10).
