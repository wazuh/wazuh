Evidence — parent objective #37203 "Container runtime security"

Source: https://github.com/wazuh/wazuh/issues/37203 (fetched 2026-07-13; state OPEN, labels level/objective + type/enhancement, no comments).

The two-module split (Description, verbatim)

This objective proposes creating two independent modules: the Container Instances Security
Module described here, and a new eBPF Module that extracts the eBPF engine out as a
standalone, shared runtime telemetry provider. The Container Instances Security Module acts
as a passive enrichment source: security modules (FIM, IT Hygiene) consume raw events and
state from the eBPF Module and query the Container Instances Security Module to enrich each
event and state with container-level context (container ID, image, namespace, pod name,
labels, etc.). Enriched events and states are delivered to the Wazuh Agent over a socket,
which forwards them to the Wazuh Server using the existing state synchronization
infrastructure.

Also: "The first supported orchestration platform integrations are Kubernetes and Docker (replacing the current Docker Listener approach). The first supported use cases are FIM and IT Hygiene, both via the eBPF provider (IT Hygiene coverage TBD)."

NFR4 — the requirement this spike implements (verbatim)

4. Extract the eBPF engine into a new, independent eBPF Module, decoupled from Container
Instances Security, serving as a shared runtime telemetry provider for FIM and IT Hygiene,
and extensible to other security modules in the future.

Implementation restrictions (verbatim, abridged)

1. The module must act as a passive enrichment source queried by the security modules, not
as a primary event producer. [= the Container module]
2. The eBPF Provider is the source of low-level runtime events (file activity, process
execution, network activity, etc.) consumed by the security modules.
3. Enriched events and states must be delivered to the agent over a socket and forwarded to
the server through the existing state synchronization infrastructure.
4. Supported agent platforms (eBPF, Kubernetes, Docker versions) are to be defined.
[← #37396's compatibility matrix feeds this]

Correlation sources (FR6, verbatim list)

PID, cgroup identifiers, namespace identifiers, container IDs, runtime metadata.

The four expected spikes (Notes §3, verbatim)

1. Correlation mechanism: determine the best runtime identifiers for eBPF correlation
(PID, cgroup, namespace, container ID).
2. eBPF compatibility: evaluate kernel compatibility and fallback mechanisms. [≈ #37396]
3. FIM integration: determine required changes to support container-aware monitoring.
4. IT Hygiene integration: identify inventory sources that can leverage eBPF collection.

Other load-bearing facts

  • FR3: "Replace the Docker Listener with a generic container runtime connector."
  • FR9: container states go to the same wazuh-states-* indices as endpoint states.
  • FR11: config block container_security / container_instances (enabled, type, path, credentials).
  • NFR3: configurable item limits on FIM/IT Hygiene for stability.
  • Note 1 (assumption): "eBPF events can be correlated with a container runtime."
