# 12 — Acceptance criteria

What F9c-2 must demonstrate for the sender to be considered done. Each criterion is checkable by a
person with a devcontainer, and F9c-2's subplan closes against this list.

The criteria were checked against the implemented sender's code (not by running it). Three cannot
be met by the current code and are marked **Not met** in place: AC-I (the documented
`server_vd_workers`), AC-J (the second signal) and AC-K (both halves). The rest describe behaviour
the code has; whether a given run demonstrates them is for that run to show.

| AC | Criterion | How it is shown |
|---|---|---|
| **AC-A** | Builds and vets clean, no cgo | `go build ./...` and `go vet ./...` succeed; `file` on the binary shows a static-ish Go executable |
| **AC-B** | Token parity with remoted | The frozen `wazuh-agent+jwt` vector self-test passes, and a bearer-authenticated request against the REAL manager returns something other than `401` for every route used (`/control`, `/stateful`) |
| **AC-C** | Enrollment works against a manager with the INSTALLED enrollment policy | A run with `fleet.agents: 3` against a manager whose `<use_password>` was not touched enrolls 3 agents over `POST /enroll` with an enrollment token and records their ids in `meta.agents_enrolled` (with `meta.bootstrap: "enroll-token"`); the ids appear in the manager's `client.keys`. The same run with `--bootstrap 1515` against a password-free authd produces the same three ids |
| **AC-D** | Control traffic is real and its answers are discarded | A 60 s run with `keepalive_interval: 5s` and 3 agents shows ~36 `control_notify_ok`; the code contains no read of `limits`, `agent.groups`, `config_hash`, `settings_hash` or `tasks` beyond validation (reviewable by grep) |
| **AC-E** | `uds` mode drives the server alone | A run against the QA harness (`inventory_sync_server_testtool --serve --no-vd`, see [`qa/README.md`](../../../../src/wazuh_modules/inventory_sync_server/qa/README.md)) produces `sessions_ok > 0` and documents visible in the indexer |
| **AC-F** | Both modes run the same scenario | One scenario file, two modes, two artifact sets whose `meta.mode` differ and whose session counts match |
| **AC-G** | The contract paths are reachable on purpose | Dedicated scenarios produce, each in its own run: a `413`, a `503` without `Retry-After` (with `retry.enabled: false`, so the sheds are counted rather than retried away), a `409`, and a `400` from a `raw` step — each counted in its own column, and none of them alone sets a non-zero exit code (a scenario's own `expected` block may still judge them). The `413` needs a manager configured with a body cap below the scenario's ~13 MB sessions (`SCENARIOS.md`, `contract_oversized_413`) |
| **AC-M** | Heterogeneous fleets run in parallel | The mixed-fleet scenario (two fleets, each several inventory lanes plus an engine lane) runs; `by_fleet` and `by_lane` in the summary show the per-fleet and per-lane breakdown, and the engine lane's `stateless_202`/`events_sent` are non-zero and isolated from the session counters |
| **AC-N** | Records everything, judges nothing — unless the scenario opts in | Without an `expected` block the summary contains no verdict field and a deliberate flood of `503`s still exits `0`; every status and every latency is present per-lane and per-fleet. With one, the verdict is over final counters only |
| **AC-O** | The opt-in verdict is strict and hardware-independent | A scenario with an `expected` block that holds exits `0` with `expected.passed: true` in the summary; one that fails exits `3` with each failure naming counter, operator and actual value; a typo'd counter or operator refuses to load; latency/throughput cannot be asserted |
| **AC-P** | Bare-503 retry behaves like an agent | Against a saturated server, a default-retry scenario shows `retries_503 > 0` and recovered `sessions_ok` for sessions that first answered `503`; attempts consume `requests_per_second` tokens; `retries_exhausted` counts abandoned sessions; `retry.enabled: false` restores pure shed counting |
| **AC-Q** | Engine rate is in real event units, per agent | An engine lane at `events_per_second: N` with `events_per_batch: B` ships `ceil(lines/B)` requests per pass and sustains ~N `events_sent`/s per agent regardless of B (a run's `events_sent`/s totals ~N × agents running the lane); `stateless_sent` counts requests and `events_sent` counts `E` lines |
| **AC-R** | zstd compression is faithful to remoted's contract | Compression is the agent-mode DEFAULT (absent resolves to zstd there, plain on uds); an agent-mode scenario run with `--compression none` vs the default produces the same `sessions_ok` (and passes the same `expected`) with a smaller `bytes_sent` compressed; authentication is independent of the body (the bearer binds only the agent's identity), so compressed requests draw no `401`s; `raw` steps stay uncompressed; `--compression zstd` with uds mode (and an explicit `"zstd"` in a uds scenario) is refused up front. The full-fidelity Windows FIM first sync (~26 MB) is REJECTED at remoted uncompressed: it is over the 10 MiB transport cap, so the connection closes without a response and the failure is recorded in `transport_errors` (a body between the 5 MiB authenticated-body cap and 10 MiB would get a `413` instead). Either way the run fails its `expected` (exit 3). That rejection is remoted's documented contract, and the reason `real_first_connect` relies on the zstd default |
| **AC-S** | The VD re-scan request is its own path, and is not confused with a session's scan | A `scan_vd` step against a manager whose feed is loaded records `scan_200` and, once the Task Manager has run the recorded `vd_scan` tasks, ONE `reason=feed_update` scan per agent in modulesd's log, distinct from the `option=VDFirst` scan the same lane's inventory session produced; the offset it declares is the one learned from `/control` (a deliberate `feed_offset` override answers `409` and is counted in `scan_409`, not as a failure); the step is refused at load time in `uds` mode and when given any payload field; `scan_sent` and its latency appear in `bench.csv`, per lane and per fleet in the summary, and are assertable through `expected.scan.*` |
| **AC-H** | Feed retry works | With a manager whose CVE feed is still downloading, a VD scenario shows `sessions_503_retry_after` and `retries_feed` > 0 and eventually `sessions_ok` > 0, without exceeding `--feed-timeout`; a budget that runs out is counted in `retries_exhausted` |
| **AC-I** | Artifacts match [09](09-metrics-and-output.md) exactly | Header of `bench.csv` compared field by field with the document; `sender_summary.json` validated against the documented shape (a JSON-schema check is **RECOMMENDED**). The header matches (`csvHeader` in `internal/metrics/csv.go`). **Not met for `meta`:** the documented `server_vd_workers` field is not produced |
| **AC-J** | Drain is clean and bounded | SIGINT mid-run drains within the drain window (`pacing.drain_timeout`; the `--drain-timeout` flag has no effect), sends `shutdown` per agent, writes complete artifacts, and reports `abandoned_on_drain` honestly; a second SIGINT exits at once. **Not met:** a second signal is caught like the first and does nothing |
| **AC-K** | Failures are loud | A deliberately wrong key produces an immediate abort naming the signing input, not a run full of `401`s; a deliberately deep working directory produces the `AF_UNIX` path error up front. **Not met:** a wrong key does not produce a run full of `401`s, but it is not an immediate abort either: the readiness probe retries the `401` until its budget (`--enroll-settle`, at least 30 s) runs out, then exits `2` without printing the signing input. The socket path length is not checked |
| **AC-L** | Reproducibility | Two runs of the same scenario with the same seed send byte-identical payloads (verifiable by hashing the generated documents) and record identical `meta` except timestamps |

## Out of scope for these criteria

Absolute performance numbers are **not** an acceptance criterion of the tool: they are the deliverable
of F9c-4, and any target here would prejudge the baseline the report is supposed to establish. The
tool is done when it measures faithfully and fails loudly — not when it reaches a particular
throughput.
