# Issue question coverage — every question the six issues ask, and where it stands

The five spikes and their parent objective pose their own design questions, in their *Open questions*,
*Angles to explore*, *Deliverables* and *Acceptance criteria* sections. This document extracts them,
one row each, records what this branch actually answers, and names the alternatives that were
available for each — so the answer can be ratified or overturned on its merits rather than by default.

- **Source:** the issue **descriptions** of
  [#37203](https://github.com/wazuh/wazuh/issues/37203),
  [#37382](https://github.com/wazuh/wazuh/issues/37382),
  [#37532](https://github.com/wazuh/wazuh/issues/37532),
  [#37533](https://github.com/wazuh/wazuh/issues/37533),
  [#37534](https://github.com/wazuh/wazuh/issues/37534),
  [#37837](https://github.com/wazuh/wazuh/issues/37837) — read 2026-09-24, not their comment threads
- **Checked against:** `37532-5-0-0-container-integration`, verified at `9ced58d751`. The branch has
  since been rebased onto `origin/main` (tip `996ddd294c`); every commit replayed content-identical,
  so the file and line references below still hold
- **Date:** 2026-09-24

> **How this differs from [16](16-open-design-questions.md).** Doc 16 asks what still needs deciding,
> and was derived from *this analysis*. This document runs the other way: it starts from what the
> **issues themselves** asked and marks each one answered or not. Rows that are still open point at
> their Q-number in doc 16 rather than restating the argument.

> **How to review this.** Read *Where this branch stands* and *Other implementation options* as a
> pair: the first is the answer on the table, the second is what else was on it. A ✅ row is not a
> request for agreement — it is a decision already load-bearing in the code, and the options column
> says what reversing it would cost. A ❌ or 🟡 row is where the options column is a menu rather than
> a record. Where a row names no alternative, that is deliberate: some rows are documents or
> signatures, and the only way to close them is to produce one.
>
> **The Decision column is yours to fill in.** Each cell already offers only the verbs that fit that
> row — a row whose answer is a signature does not offer `keep`, and a row blocked on a benchmark does
> not offer `change`. Pick one, delete the rest, fill in anything after a `→`, and sign it. A cell
> still showing its untouched menu means nobody has ruled on that row yet, which is worth being able
> to see at a glance.

## 17.1 Status legend

| | Meaning |
| --- | --- |
| ✅ | **Resolved** — decided, implemented, and verified on a real node |
| 🟢 | **Implemented, unverified** — the code exists; no end-to-end evidence was taken |
| 📄 | **Answered on paper** — written up in these documents, never ratified by the owner the issue names |
| 🟡 | **Partial** — the row states which half does not hold |
| ❌ | **Open** — no answer |
| ➖ | **N/A** — out of this branch's scope by the issue's own wording |

### Decision vocabulary

| Write | Offered on | Means |
| --- | --- | --- |
| `keep` | rows with an answer (✅ 🟢 📄 🟡) | ratified as built. The three divergences in [§17.9](#179-what-the-tally-does-not-show) need exactly this before they stop being unratified |
| `change → <option>` | rows with an answer you are overturning | name the option from *Other implementation options*; the cost of switching is scoped there |
| `adopt → <option>` | ❌ rows that are a genuine choice | pick from the menu in the fifth column |
| `produce → <who, by when>` | rows whose answer *is* an artifact | the RBAC manifest, the failure matrix, the volume-type table, the unavailable-options table, a signature. Approving of its absence changes nothing — someone has to write it |
| `measure` | rows blocked on evidence | needs a real node and an afternoon, not a ruling |
| `defer → <release or owner>` | anywhere | out of scope for now, said out loud. A named deferral is a decision; silence is not |

**Worked example.** Row [#37203 8](#172-37203--the-objectives-own-open-questions-and-requirements) ships as
`☐ keep ☐ change →`. Ratifying the config surface as built leaves `keep — RV 2026-09-24`. Sending it
back to the FR as written leaves `change → implement FR11 literally — RV 2026-09-24`.

parts of the design and they are decided, implemented and in several cases proved by racing the case
they were supposed to handle. That is the substance of four spikes.

**Four kinds of thing dominate the 23 open rows**, and only one of them is design work:

1. **Sign-offs and decision records** (#37382 A5/A10/B18, #37532 5a/5b, #37534 1). Content that exists,
   in a form or with an approval that does not. Cheap, and blocking issue closure rather than code.
2. **Measurements never taken** (#37532 1d/7b, #37382 B14, #37837 4). Each needs a real node and an
   afternoon; several open decisions are explicitly waiting on them.
3. **The server side** (#37837, all five). Not started, externally owned, and the reason the stateful
   half of the feature delivers nothing today.
4. **One genuine design gap**: #37534 rows 2 and 3 with #37203 row 4 — **Syscollector was specified as
   an eBPF consumer and is not one.** It polls. Everything else on this list is a decision, a document
   or a measurement; this is the one place where what was built differs in kind from what was asked.

**Three answers diverge from what the issues specify**, each defensibly, none ratified:

| Issue says | Branch does | Why it is arguably better |
| --- | --- | --- |
| FR11: `type`, `path`, `credentials` | nested `<kubernetes>` / `<docker>` blocks with typed children | typed per runtime, validates at parse time, and makes the dual-runtime case expressible — which a single `type` cannot |
| #37533 3a: reconstruct a host path by longest-prefix match against OCI mounts | address through `/proc/<pid>/root`; use the mount list as a **traversal policy** instead | the kernel does the mount resolution; the mount list then buys a `hostPath: /` escape guard the specified algorithm would not have |
| #37532 1: locate the overlay `merged` dir per runtime | `/proc/<pid>/root` for every runtime | one code path for Docker, containerd and CRI-O, and no snapshot-layout knowledge to maintain |

Each of these is a good decision recorded in the wrong place: in the code, and in an analysis
document, rather than in the issue that asked the question.

## 17.10 A second implementation of #37396 exists

`enhancement/37396-spike-poc-design` (Miguel Angel De la Vega Rodriguez, last commit 2026-09-01, **no
pull request open**) answers #37396 differently from this branch. Neither branch contains any part of
the other — checked both ways, zero files. Both descend from mainline's `syscheckd/src/ebpf/modern.bpf.c`.

| | POC branch | This branch |
| --- | --- | --- |
| Module path | `src/shared_modules/ebpf/` | `src/shared_modules/ebpf_provider/` |
| Interface | C++, `namespace wazuh::ebpf`, class `EbpfLoader` | C, opaque `rt_handle_t`, `rt_open` / `rt_poll` / `rt_close` |
| Kernel program | `modern.bpf.c`, refactored to 637 lines "into one readable file" | `rt_file.bpf.c` → `rt_file.bpf.o` |
| syscheckd | **deletes** `syscheckd/src/ebpf/`, consumers use the shared module (`fim_ebpf.cpp`) | **keeps** mainline `syscheckd/src/ebpf/` and adds the provider beside it |
| BPF objects loaded | one | **two** — `ebpf_whodata.cpp:33` opens `modern.bpf.o`, `rt_engine.c:49` opens `rt_file.bpf.o` |

**They converged on the same event contract independently.** The POC's
`FileEventType {OPEN_CREATE=1, ATTR_CHANGE=2, UNLINK=3, RENAME=4}` is this branch's
`RT_EV_FILE_OPEN / ATTR / UNLINK / RENAME` in the same order, and both stamp `cgroup_id` on every
event. Two authors reaching the same taxonomy is evidence the taxonomy is right, and it means the
two are closer than the file layouts suggest.

**Four differences decide which one wins:**

1. **In-kernel cgroup filtering — the decisive one.** This branch's kernel program carries 29 cgroup
   references; the POC's carries two, and they are `__u64 cgroup_id;` and `bpf_get_current_cgroup_id()`.
   The POC *stamps* the cgroup and filters nowhere: no cgroup mode, no allowlist, no per-cgroup drop
   accounting. Container FIM is built on all three ([D4](12-blocking-decisions.md), [D14](12-blocking-decisions.md)).
   Adopting the POC wholesale would mean rebuilding them.
2. **LSM coverage, where the POC is ahead.** It attaches `lsm/path_rename` and `lsm/path_unlink` as
   well as `lsm/file_open`; this branch attaches only `lsm/file_open` and falls back to kprobes for
   unlink, rename and attr.
3. **ABI versioning, where this branch is ahead.** Every `rt_file_event` carries `abi_major`, with
   `rt_abi_major()` / `rt_abi_minor()` and a documented MINOR-1 extension (`cwd`, `parent_cwd`,
   `parent_comm`), plus `mnt_ns` and a `dropped` counter. The POC's `FileEvent` is a plain struct with
   no version field, which a separately-shipped module cannot afford.
4. **Multi-class scaffolding.** The POC declares `EventClass { FILE, PROCESS, NETWORK }` with the last
   two marked *"not implemented yet"*. This branch is file-only by name and construction, so the
   eBPF-driven inventory that [#37534 rows 2 and 3](#176-37534--it-hygiene-syscollector-integration)
   ask for would need a second provider here and an extension there.

**What this changes in the rows above.** [#37203 row 11](#172-37203--the-objectives-own-open-questions-and-requirements)
is still ✅ — NFR4 is satisfied — but its alternative is no longer hypothetical, and the duplicated BPF
load it implies is [16 Q15 / D9](16-open-design-questions.md#q15--do-two-ebpf-engines-ship-or-does-a4-land-first-d9)
in concrete form. Ratifying that row now means ratifying two engines over one, with a built
alternative on the table.
